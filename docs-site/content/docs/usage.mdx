# 用法

**本页回答**：这个插件怎么装进一个 home、要配哪些设置、agent 与人分别从哪儿操作它、怎么确认备份真的在运行。

## 装进 home

在工作台里依次调：

```text
plugin-manager.install {"pkg":"@cordisjs/plugin-timer"}
plugin-manager.install {"pkg":"@godcreator/gwb-windows-backup"}
```

本插件的定时器用官方的 `@cordisjs/plugin-timer`（公共 npm），插件管理不替它装，要单独装。
**home 里没有 timer 条目时本插件整个停在等待**——顶层 `inject` 是等待语义，宁可等待，
不在没有定时器时假装在备份。

{/* ref file="../src/index.ts" lines="91-91" */}

数据目录由数据插件按条目 id 给出（插件管理默认给的条目 id 是 `windows-backup`，即
`<home>/data/windows-backup`），全部用户数据住那里。装完把 restic 本体放进 `bin/restic.exe`
（或用 `restic-exe` 设置指向别的位置）——装 restic 是一次性手工操作，代码不代办。

## 设置（17 个键，kebab-case）

设置经 gwb-settings 声明，**每次跑现读现用、绝不缓存**——设置插件没有变更通知，缓存一份
就会「设置改了、跑的还是旧值」。类型不对或缺字段的值按默认值处理，不报错。

{/* ref file="../src/index.ts" lines="94-118" */}

必填两项：`sources`（备份白名单，在设置插件里一行一项；分号分隔的一整串也认）与 `local-repo`
（本地 restic 仓库路径）。缺任何一项，定时照常触发，但每轮都拒跑，拒跑理由是一句指路的话。

**往白名单里加路径的代价**：restic 挑父快照是按 `host,paths` 分的组——**加了路径就是新组、
一个候选都没有**，那一轮会把全部源重读重算（本机实测 51 GiB / 452k 个文件，`gomaxprocs: 1`
时约 90 分钟，本地与 OSS 各一遍）。插件把最近一次成功的快照 ID 记在 `state.json` 里、显式传
给 restic 当父快照，于是**只有新加的那条路径要真读**；**减路径、改顺序都不付这个代价**（老快照
仍是当前路径集的超集，可以当父快照）。想再快一档就把 `gomaxprocs` 调大——必须全读的那种
一轮（第一次备份一条新路径、`state.json` 丢了）是它唯一能帮上大忙的地方。

排除规则是**两层合并**：内置基线（包内通用垃圾清单：node_modules、dist、构建产物、
临时文件等，随版本走）总在生效；`exclude` 设置键追加自己的规则（一行一条 restic 模式，
`#` 开头的行是注释）。数据目录里的 `restic-exclude.txt` 不读，规则要写进 `exclude` 设置键。

{/* ref file="../src/backup.ts" lines="117-133" */}

OSS 三项（`oss-bucket` / `oss-endpoint` / `oss-repo-path`）只在 `oss-enabled` 开着时才被
要求；凭据不进设置——`credentials/oss-credentials.txt`（KEY=VALUE，支持 `export ` 前缀、
引号、`#` 注释）。仓库密码放 `credentials/restic-password.txt`，内容任何时刻都不进本进程。

## 命令（六条，agent 经 MCP 入口的 `run` 调用）

{/* ref file="../src/index.ts" lines="454-603" */}

| 命令 | 干什么 |
| --- | --- |
| `windows-backup.run` | 立刻跑一轮完整备份（= 定时那轮做的事）；占不到锁、配置没填全、这轮失败都会如实说——失败不拿上一轮的成功冒充 |
| `windows-backup.check` | 立刻跑一次五项健康检查，回全量状态 |
| `windows-backup.status` | 回全量状态（上次备份、自检结论、定时器节奏）——窗格轮询的就是它 |
| `windows-backup.paths` | 回数据目录全部路径——看凭据在不在、tail 日志，先调这条拿路径，别猜 |
| `windows-backup.restic` | 透传一条 restic 命令（如 `{ "repo": "local", "args": ["snapshots"] }`），自动补 `--repo` 与 `--password-file`，密钥不出现在参数里。恢复快照也走它：`args: ["restore", <id>, "--target", <目录>]` |
| `windows-backup.mark` | 补记周期动作时间戳：`{ "what": "usb-copy" \| "exclude-audit" \| "review", "at": "YYYY-MM-DD" }` |

## 怎么确认备份在运行

1. `windows-backup.status`：`backup.lastRunOk` 是 `true`、`nextRunAt` 在未来；`backup.running`
   为 `true` 时再看 `runningSince`——这一轮是从什么时候开始的，小时级的一轮（首次全量那种）只凭
   一个 `running` 分不清是在干活还是卡死了；
2. `windows-backup.check`：五项没有 problem；
3. 有疑问直接看日志（`windows-backup.paths` 拿路径）：最后一轮末尾应有
   `Backup completed successfully`。

加载后 30 秒是第一轮：先自检，上一轮备份太旧（超过一个周期）就顺带补跑一轮。不在加载时
当场跑——加载期间所有插件都在启动，这时运行 restic 会让仓库 I/O 拖慢启动。

{/* ref file="../src/index.ts" lines="605-622" */}

**工作台没运行就不备份**——定时器在 gwb 工作台里，工作台关了备份就停，下次启动 30 秒后
补跑。这是有意接受的代价；要不依赖工作台的保底，等路线上的灾难恢复命令行入口。
