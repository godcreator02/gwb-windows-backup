# 锁

**本页回答**：两轮备份怎么保证不叠在一起、崩过一次的锁为什么不会把备份永久停摆。

`src/lock.ts`。零第三方依赖，只用 node 内置——这是 `src/` 域库的硬约束。

## 管什么

数据目录里的 `backup.lock`：`{ pid, lease, startedAt, beatAt }` 四格。闭包里的布尔（宿主层
`state.backing`）挡得住**同一个进程**里的重复触发；锁落在磁盘上是为**跨进程**的场面——另一个
home、另一个入口同时起一轮，谁也不认识谁。两层并发保护缺一不可。

**不知道什么**：不知道锁外头是谁在跑、跑什么；不认识备份管线，只管「这一个文件里的
字段谁写的」。

进程不在（`process.kill(pid, 0)` 抛 `ESRCH`）= 上一轮崩了或断电了，锁文件留在那儿没人删
——不认这一支，一次崩溃让备份永久停摆且毫无症状。`EPERM` 算活着（进程在，只是没权限碰）。
心跳静默超上限那支兜底 pid 被系统回收给别的进程的场面——**判的是心跳停了多久，不是这轮
跑了多久**：一轮可以合法地串四个六小时上限的子步骤，持锁方每五分钟 `renew()` 跳一次心跳，
干得再久的活任务也不会被当死锁抢走；只有心跳真的停了的才轮到别人接管。

## 提供的接口

| 接口 | 契约 |
| --- | --- |
| `acquire(file)` | **原子占锁**（`flag: 'wx'`，只有一个赢家）；占到了回持有句柄 `{ release, renew }`，别人在跑回 `null` |
| `held.release()` | **只删 lease 对得上的那份**——被抢的那方晚一步来删，删不掉新主人的锁；同 pid 的两代任务也分得清 |
| `held.renew()` | 心跳：把 `beatAt` 刷到现在。只动 lease 对得上的那份，锁已被抢走后是空操作 |
| `readLock(file)` | 不存在 / 坏掉 / 形状不对一律 `null`，都按「没有有效的锁」处理 |
| `isStale(lock)` | 上面那两支判据 |

删不掉锁不抛：备份已经跑完了，为一个删不掉的锁文件把结论弄坏不划算，下一轮按陈旧抢过来。

## 依赖的接口

无注入就不依赖本仓任何模块；`LockOptions` 收 `pid` / `lease` / `now` / `alive` 四个注入点，
测试不真起进程、不真等 6 小时。

## 怎么单独测

`tests/lock.test.ts`：注入假 `alive` 与拨钟，证明「活进程的新锁挡人、死进程的锁被接管、
心跳静默过期、释放只删自己的租约、同 pid 两代分得清、心跳让干得久的活任务不被抢」。
