**本页回答**：两轮备份怎么保证不叠在一起、一次崩溃留下的锁为什么不会让备份永远停住、被抢走的锁为什么删不掉新主人的。

`src/lock.ts`，只用 node 内置模块。并发保护有两层：宿主层闭包里的 `backing` 挡**同一个进程**里的重复触发；这把锁落在磁盘上，
挡的是**另一个进程**——另一个 home、另一个入口同时起的一轮，彼此并不认识。唯一的生产调用方是[备份管线](/docs/modules/pipeline)的 `runFullBackup`。

## 锁文件里有什么

`{ pid, lease, startedAt, beatAt }`。`lease` 是这次占锁的租约 id，释放与心跳都只认它：同一个进程先后两轮共用一个 pid，只认 pid
会让新旧两轮互相删锁。`beatAt` 是最后一次心跳，持锁方每 5 分钟刷一次：

{/* ref file="../plugins/windows-backup/src/lock.ts" lines="8-10" hash="9ece4c2a7547" blob="b3a442ee3f59" */}

旧格式的锁没有 `lease` 与 `beatAt`，读到时按可选字段处理，心跳退回用 `startedAt`。

## 什么时候算无主

命中任一条就当陈旧，直接接管：

{/* ref file="../plugins/windows-backup/src/lock.ts" lines="48-55" hash="25b313ab4ab6" blob="b3a442ee3f59" */}

- **进程不在了**（`process.kill(pid, 0)` 抛 `ESRCH`）：上一轮崩了或机器断电，锁文件没人删。不认这一条，一次崩溃就让备份永远停住，
  而且没有任何症状。`EPERM` 算活着：进程在，只是属于别的账户
- **心跳停了超过 6 小时**：判的是心跳停了多久，不是这一轮跑了多久——一轮可以合法地串起好几段、每段都跑到 6 小时上限，
  心跳一直在跳就不会被抢；pid 被系统回收给了别的进程时，也靠这一条接管

## 占锁与释放

- **占锁是原子的**：用 `flag: 'wx'` 创建，同时来的两个只有一个成功。先读、再判、再写的三步写法，在跨进程时两边都会以为自己占到了，
  两轮 restic 并发跑
- 文件已经在：只有它确实无主（陈旧，或读不出有效形状）才删掉重抢；重抢时又撞上，就是别人刚抢到，回 `null`
- **释放只删租约对得上的那一份**：抢过陈旧锁的新主人正在跑，被抢的一方晚一步来删，删不到新主人的锁
- 删不掉、心跳写不进都不抛：备份已经跑完了，为一个锁文件把结论弄坏不值得；删不掉的锁下一轮按陈旧接管

## 测试

`tests/lock.test.ts` 注入假的「进程在不在」与假时钟，查：活进程的锁挡住后来者、死进程的锁被接管、心跳停了超时被接管、
心跳还在跳的老锁不被抢、释放只删自己的租约、同一个 pid 的两轮分得清、锁被抢走后心跳不改别人的锁、旧格式按 `startedAt` 判。
