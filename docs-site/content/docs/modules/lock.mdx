# 锁

**本页回答**：两轮备份怎么保证不叠在一起、崩过一次的锁为什么不会把备份永久停摆。

`src/lock.ts`。零第三方依赖，只用 node 内置——这是 `src/` 域库的硬约束。

## 管什么

数据目录里的 `backup.lock`：`{ pid, startedAt }` 两格。闭包里的布尔（宿主层 `state.backing`）
挡得住**同一个进程**里的重复触发；锁落在磁盘上是为**跨进程**的场面——另一个 home、
另一个入口同时起一轮，谁也不认识谁。两层并发保护缺一不可。

**不知道什么**：不知道锁外头是谁在跑、跑什么；不认识备份管线，只管「这一个文件里的
两格谁写的」。

进程不在（`process.kill(pid, 0)` 抛 `ESRCH`）= 上一轮崩了或断电了，锁文件留在那儿没人删
——不认这一支，一次崩溃让备份永久停摆且毫无症状。`EPERM` 算活着（进程在，只是没权限碰）。
超过 6 小时那支兜底 pid 被系统回收给别的进程的场面——备份超时上限就是 6 小时，跑得比这
还久的 restic 早被自己的超时杀了。

## 提供的接口

| 接口 | 契约 |
| --- | --- |
| `acquire(file)` | 占到了回**释放函数**（幂等、绝不抛）；别人在跑回 `null` |
| `release(file, pid)` | **只删 pid 对得上的那份**——抢过陈旧锁的新主人正在跑时，被抢的那方晚一步来删，删掉的就是新主人的锁 |
| `readLock(file)` | 不存在 / 坏掉 / 形状不对一律 `null`，都按「没有有效的锁」处理 |
| `isStale(lock)` | 上面那两支判据 |

删不掉锁不抛：备份已经跑完了，为一个删不掉的锁文件把结论弄坏不划算，下一轮按陈旧抢过来。

## 依赖的接口

无注入就不依赖本仓任何模块；`LockOptions` 收 `pid` / `now` / `alive` 三个注入点，
测试不真起进程、不真等 6 小时。

## 怎么单独测

`tests/lock.test.ts`：注入假 `alive` 与拨钟，证明「活进程的新锁挡人、死进程的锁被接管、
6 小时过期、释放只删自己的」。
