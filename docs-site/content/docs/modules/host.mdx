**本页回答**：域库怎么接到工作台上、哪些服务缺了会让备份停、哪些缺了只是没有界面、运行时状态放在哪。

`src/index.ts`。全部加载动作在 `mount(ctx, deps)`，`apply` 只是外面一层，负责传入会启动子进程的两个生产实现；拆成两层是为了测试把它们换成替身。
宿主层只认 `HostContext` 这个最小形状，不 import 内核的运行时代码；它和工作台插件之间的每条连接见首页[接缝 1–5](/docs#接缝逐条)。

## 顶层注入是等待语义

`export const inject` 列的服务缺一个，cordis 就不调用 `apply`，整个插件（连同备份）停在等待，日志里写明在等谁。所以顶层只列离了就没法备份的四个：
命令总线、设置、数据、定时器；外壳走局部注入，缺了只是没有窗格。

## 运行时状态

`createBackupRuntime` 把可变状态放在这一次 `mount` 的闭包里：自检进行中、上一次自检的结论与时间、下一次自检时间、自检本身出错时的那句话、
两个定时器的间隔、下一轮备份时间，以及第一层并发保护 `backing`。重新加载就清零（上一次自检的结论没了，30 秒后重新自检）——
结论本来就是「此刻的观察」，不值得另存一份文件；要跨进程保留的几项在 `state.json`。

`status` 回执里的 `backup.runningSince` 取自 `backup.lock` 的 `startedAt`：「这一轮跑了多久」是最常被问的一句，几个小时的一轮只看 `running` 分不清是在干活还是卡住了。

## 定时器每次触发都往后推「下次」

{/* ref file="../plugins/windows-backup/src/index.ts" lines="245-255" hash="959f8a9b7c88" blob="7eec32c17df0" */}

只在开定时器时算一次 `nextRunAt`、触发后不推的话，状态里显示的永远是一个已经过去的时刻。设置里改了频率，下一轮开跑时用现读的值核对，
变了才停掉旧的、按新值重开；自检间隔没变时只把下次时刻往后推，不重开——重开会让当前这一轮的计时清零。

`runBackup` 与 `runCheck` 都**绝不抛**：定时器与命令两条路都调它们，抛出去周期定时就停了；所有异步调用自己 catch 并写日志，
静默的 reject 在日志里什么都不留，现象是「加载了，但什么都没发生」。

## 版本号

`status` 里的版本号从插件包根的 `package.json` 读，本模块在 `dist/index.js`，所以相对路径是上一层；loader 可能带查询串 import 本模块，
`createRequire` 拿那种地址解析相对路径会抛错，先去掉 `?` 后面那段。另有 `moduleLoadedAt`（模块被 import 的时刻）与 `appliedAt`：
重新安装后这两个时刻没变，就是新代码没加载上。

## 外壳走局部注入

{/* ref file="../plugins/windows-backup/src/index.ts" lines="554-572" hash="aeae7c0d9079" blob="7eec32c17df0" */}

没装外壳的 home 里备份照常，缺的只是窗格；把外壳写进顶层注入的话，外壳不在时整个插件连同备份一起停在等待，那才是事故。

## 测试

`tests/plugin.test.ts`：假宿主（`effect` 只记下注销函数，设置、命令、外壳全是内存表）加两个替身，查首次自检与补跑的时机、`nextRunAt` 往后推、
改了频率后重建、命令回执的形状、设置现读、中途抛错回本轮失败、外壳不在时照常加载、卸载后命令与设置全部注销。先读 `mount`，再读 `createBackupRuntime`。
