占到锁以后，持锁期间每 5 分钟刷一次心跳：锁的陈旧判定看心跳停了多久，不看这一轮跑了多久，所以一轮串起好几段、
每段都能跑到 6 小时上限，也不会被下一轮当成死锁抢走（见[锁](/docs/modules/lock)）。占不到锁直接回
`{ ok: false, skipped: 'locked' }`，**不写失败日志、不弹通知、不动 `state.json` 里的上一轮结论**——另一轮正在跑不是故障，
记成失败会让五项自检误报。

顺序是：本地备份 → 本地 prune（每天一次）→ OSS 备份 → OSS prune → 日志轮转 → 写 state.json → 通知。三条决定后面跑不跑的判据：

- **本地备份失败，后面全不跑**：本地都没成，OSS 备份的是同一批源，多半是同样的失败
- **prune 每天一次，真成功了才记 `lastPrune`**：失败了下一轮再试。每次 forget 之前先 `restic unlock`，它只删陈旧锁——
  被打断的备份留下的锁不挡下一次备份，却会让要排他锁的 prune 天天失败（轨迹卡[prune 按主机分组](/trajectory/2026-09-25-prune-group-by-host)）
- **OSS prune 要本轮该 prune、且 OSS 备份成功**（不看本地 prune 成没成）：往一个刚备份失败的仓库上跑 forget，等于拿不完整的快照集算保留窗口

不管成败，最后都记 `lastRunAt` / `lastRunOk` / `lastRunSummary`。只在成功时记的话，连着失败三天看起来会像「三天前刚备过」：

通知三种：本地失败是 `Restic Backup FAILED`（正文带日志路径，收到通知的人下一步就是看日志）；全成是 `Restic Backup OK`；

## 父快照

两次 `restic backup` 都从 `state.json` 取一份快照 ID 交给 `--parent`：本地仓用 `lastLocalSnapshot`，OSS 仓用 `lastOssSnapshot`，
两个仓的快照链各自独立、ID 不通用。

**为什么显式给**：restic 自己挑父快照时按主机加路径分组，**白名单里加了一条路径就成了新的一组，一个候选都没有**，
于是所有文件重读一遍（实测 51 GiB、45 万个文件，单线程约 90 分钟，本地与 OSS 两次就是三小时）。显式给一份父快照，
新路径当新文件读，老路径照旧按父快照比对。父快照 ID 在开跑前读一次；每段成功后立刻把新 ID 写回 `state.json`，
后面的 prune 或 OSS 段失败，也不影响下一轮用它（轨迹卡[显式传父快照](/trajectory/2026-09-20-parent-snapshot)）。

**记着的 ID 在仓库里已经没了**（仓库重建过，或 `state.json` 从更早的备份里恢复回来），restic 直接失败：stderr 一行
`no matching ID found for prefix "<id>"`、退出码 1。这时**不带父快照重跑一次**——让整轮备份败在一个只为提速的参数上，
比不要这次提速更糟。判据只认 restic 的那两句原话，别的失败一个都不重试；重跑前写的是普通说明行，不是 `Backup FAILED`
契约行，否则五项自检会把一次正常的自我修复记成故障（见[日志契约与通知](/docs/modules/log)）。

## 返回什么

`FullBackupResult` 二选一：跑完了的 `CompletedBackupResult`（`ok`、`local`、`oss`、`prunedToday`、`notification`，`skipped: null`），
或没跑成的 `SkippedBackupResult`（`skipped: 'locked'` 加占锁那一轮的开始时间 `heldSince`）。全程不抛，每一段的失败都写进日志与返回值。

对外还有两个给宿主层用的函数：`refuseReason(config)` 判配置齐不齐（定时与命令共用这一份判据），`buildNotification` 拼通知文案。
