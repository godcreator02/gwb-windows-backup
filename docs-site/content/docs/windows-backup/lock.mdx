`src/lock.ts`，只用 node 内置模块。同一时间只能有一轮备份：两轮叠在一起，restic 的 prune 会因为拿不到排他锁失败，`state.json`
也会被两边交替改写。这把锁落在磁盘上，所以同一个进程里的两次触发（定时那一跳与 `run` 命令）、插件被重新加载前后的两轮、
两个进程，挡的都是它。

## 锁文件里有什么

{/* ref file="../plugins/windows-backup/src/lock.ts" lines="4-10" hash="8c792f6df514" blob="31525a2f0aec" */}

`lease` 是这次占锁的租约 id，释放与心跳都只认它：同一个进程先后两轮共用一个 pid，只认 pid 会让新旧两轮互相删锁。
缺 `lease` 或 `beatAt` 的锁文件按「没有有效的锁」处理，下一个来的人把它删掉、重新占锁。

## 什么时候算无主

{/* ref file="../plugins/windows-backup/src/lock.ts" lines="38-52" hash="02027b692c52" blob="31525a2f0aec" */}

- **进程不在了**（`process.kill(pid, 0)` 报 `ESRCH`）：上一轮崩了或机器断电，锁文件没人删。`EPERM` 算活着：进程在，只是属于别的账户
- **心跳停了超过 6 小时**：判的是心跳停了多久，不是这一轮跑了多久——一轮可以合法地跑好几个小时，心跳一直在跳就不会被接管；
  pid 被系统回收给了别的进程时，靠这一条接管

`activeLock` 是「正在备份」的唯一判据：锁文件在、形状对、不陈旧。定时那一跳看到它就什么都不做，`status` 的 `running` 与 `runningSince` 也读它。

## 占锁与释放

{/* ref file="../plugins/windows-backup/src/lock.ts" lines="62-141" hash="076d30a2d4fb" blob="8c03b6c0f6a4" */}

- **占锁是原子的**：用 `flag: 'wx'` 创建，同时来的两个只有一个成功
- 文件已经在：只有确实无主（陈旧，或读不出有效形状）才删掉、重新占锁；重建时又得到 EEXIST，就是别人刚占到，回占不到
- **释放只删租约对得上的那一份**：接管了陈旧锁的新主人正在跑，被接管的一方晚一步来删，删不到新主人的锁
- 删不掉、心跳写不进都不抛：一轮已经跑完，为一个锁文件把结论弄坏不值得；删不掉的锁下一个来的人按陈旧接管

唯一占锁的是[一轮备份](/docs/windows-backup/round)的 `runFullBackup`：占不到就回 `skipped: "locked"`，一个字都不写。

## 测试

`tests/lock.test.ts` 注入假的「进程在不在」与假时钟，查：活进程的锁挡住后来者、死进程的锁被接管、心跳停了超时被接管、
心跳还在跳的老锁不被接管、释放只删自己的租约、同一个 pid 的两轮分得清、锁被接管后心跳不改别人的锁、缺字段的锁当没有、
`activeLock` 在持有、释放、持有者不在三种情况下的判断。
