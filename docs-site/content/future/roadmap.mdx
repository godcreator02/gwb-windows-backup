**本页回答**：这个插件还有哪些没做的事，为什么现在不做、各自在等什么。

判据仍是首页那一句：代码只做没人盯着也要一直做的事，一次性操作归手册。下面三件都来自 2.0 重写收场时留下的账
（轨迹卡[2.0 收场](/trajectory/2026-09-12-2-0-shutdown)），谁接手谁认领。那份账里的第四件「进插件市场的白名单」已经不用做：
插件管理按清单 `keywords` 里的 `gwb-plugin` 检索可装的插件，本插件的清单带着它。

| 要做的 | 在等什么 | 说明 |
| --- | --- | --- |
| **不依赖工作台的灾难恢复入口** | 真遇到「工作台起不来、备份状态查不了」的现场 | 一个不经工作台的命令行入口（如 `node dist/cli.js --data-root <数据目录>`），直接读写数据目录里的状态、触发备份。连带两样：把设置落成数据目录里的 `config.json` 快照给它读，以及经 `gwbNodeCli` 登记。没遇到之前不做第二个入口——命令行与宿主层各写一份「读状态」，迟早有一边忘了改 |
| **真 OSS 实机验证** | 一个专用的 OSS 仓库路径与独立的 AccessKey | 推送逻辑单测已覆盖；真跑要往阿里云上写数据，不能拿生产 bucket 试。到时开专用路径、独立凭据，跑一轮完整链路，读数放进 `probes/` |
| **随插件发的 AI 手册** | 手册内容从老仓搬完、按现在的写法改写 | 老仓有四份一次性操作的手册（装 restic、首次配置、USB 离机副本、灾后取数据）。做法是说明书随插件发布：插件包里加 `skills/`，宿主层局部注入 `gwbSkills` 登记，装了本插件的 agent 经 MCP 入口就读得到。此刻代码里还没有这个注入 |

另有一件在收件里等决定：`run` 与 `restic` 两条长命令要不要改成可取消、可恢复的作业接口，见
[收件](/future/inbox/2026-09-20-console-review-stale-result-lock-and-long-jobs)。
