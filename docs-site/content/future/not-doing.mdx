# 刻意不做什么

下面每一条都是**决定不做**，不是排期没排到。要做，得先推翻[判据](/future/overview)那句
「代码只装没 AI 也在的事」。写下来是为了防一件事：一年之后有人看到某处「缺了个功能」，
顺手补上，理由充分，然后再来几次。

## Veeam 整机镜像

本件管的是 restic 文件级快照。整机镜像（Veeam Agent Free 那一类）是另一套安装、另一套
调度、另一套恢复路径，它的一次性操作浓度极高——装 agent、配任务、换盘裸机恢复，每一步
都是人在现场的手工活，代码能代办的只有「提醒该做了」，而这一格五项健康里已经有
（USB 离机副本与周期维护的提醒）。把镜像的执行塞进本件，换来的只是两套调度器互相抢
盘 I/O。

什么时候补：真出现「裸机恢复要重装整个工作台环境」的现场，先写手册把步骤钉住，再谈
代码要不要接提醒之外的那截。

## 恢复编排向导

恢复不缺代码，缺的是人冷静地照步骤走：`windows-backup.restic` 透传命令就是恢复的门
（`args: ["restore", <id>, "--target", <目录>]`），仓库密码、仓库地址、密钥补全都自动。
编排向导要做的是把「选快照、选目标、校验、覆盖确认」串成一个流程引擎——它编排的那个
过程一年发生一次，流程引擎本身却要天天养；灾后现场要的是可打印的步骤清单，不是一层
可能自己出 bug 的 UI。

什么时候补：恢复步骤多到手册装不下、或者要给不认识 restic 的人代做时。

## 云盘式浏览

按快照浏览 / 预览文件（云盘那种体验）是 restic 的 restore 与 mount 已经覆盖的读路径，
本件的全部价值在**写路径**（快照、保留策略、异地副本）与**观察面**。做一个浏览器意味着
接住文件树的性能、预览的安全、大目录的分页——一整摊读侧工程，跟「备份在不在转」这个
本件要回答的问题无关。

什么时候补：出现「恢复前要先反复核对单个文件内容」的真实高频场景，先看
`restic mount` 够不够。

## 凭据保险箱

密码只交路径、AccessKey 只进子进程 env（见[凭据纪律](/docs/modules/credentials)），凭据
落在数据目录的两个文件里。保险箱要解决的是「进程内存里的密钥怎么藏」——而本件的纪律
恰恰是让密钥**根本不进进程**：不读密码内容、OSS key 用完即弃。引入保险箱等于先造一个
值得攻击的集中点，再为它配一套保护；两份凭据文件的权限盘上管，restic 的仓库加密管数据
本身。

什么时候补：出现多份凭据轮换、或凭据要跨多台机器同步的真实需求——到那时先复审
[凭据纪律](/docs/modules/credentials)整页，而不是在它上面加一层。
