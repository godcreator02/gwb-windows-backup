# gwb-windows-backup 是什么

gwb 工作台上的 Windows 个人备份插件：restic 打快照 + 阿里云 OSS 异地副本 + 周期自检 +
一个备份窗格，运行在 gwb 内核上。定时器每 30 分钟一轮（可配），工作台没运行就不备份、启动
30 秒后补跑一轮——它是给「开着这台工作台的机器」设计的备份，不是系统级的灾备服务。

从 DSH 原生插件重写而来（老仓 `D:\dshfiles\26082800ktb\god-windows-backup` 只作参考）：域逻辑
（锁、备份流程、五项健康判据、restic 参数表、日志契约行、凭据纪律）语义不变、代码重写；
接工作台的那一层整个换成 gwb 的契约——命令总线、设置插件、数据插件、外壳窗格。

## 判据：代码只做「没有 AI 也要发生」的事

这个插件做什么、不做什么，都从一句话推出来：代码只做定时备份、周期自检、状态展示这类
**没人盯着也会自己发生**的事；一次性操作——装 restic、首次配置、USB 离机副本、灾后
取数据——是人在现场的事，归手册不归代码。

推论有三条。**其一**，备份的价值在「没人管也一直在跑」，所以状态展示（五项健康、窗格、日志契约行）
与备份本体同样重要——备份断三个月没人发现，等于没有备份。**其二**，凭据纪律比便利重要：
密码只交路径、AccessKey 只进子进程 env，省下的那几行代码不值得拿泄漏风险换。**其三**，
失败要让人注意到，又不能误报：健康检查误报比漏报更伤（天天报警，真出事那次一起被忽略），所以判据
的容忍口径一律给两个周期。

## 与内核的关系

本插件运行在内核上，不是内核的一部分。`package.json` 的 peer 里只有内核包
`@godcreator/gwb-kernel-desktop`，范围写验证时那个内核的版本；命令总线、设置、数据三个插件是
备份离不开的服务，但它们由 home 里装的插件提供，本插件只 import 它们的类型，写在 dev 里，运行时经
`inject` 拿到——缺哪个，本插件就停在等待状态。外壳走局部注入：没装外壳的 home 里备份照常运行，只是没有窗格。
定时器不自己写，用官方的 `@cordisjs/plugin-timer`，由 home 里的条目提供——条目缺了本插件整个停在等待，
宁可等待，也不在没有定时器时假装在备份。
